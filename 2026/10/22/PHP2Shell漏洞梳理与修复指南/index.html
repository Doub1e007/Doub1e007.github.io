PHP2Shell 漏洞梳理：两个 9.2 分的 PHP 核心 RCE（CVE-2026-109618 / CVE-2026-109619）

发表于2026年10月22日|更新于2026年10月22日|安全
|浏览量:

2026 年 10 月 21 日，PHP 官方发布紧急安全更新，修复了两个位于 PHP 核心的高危远程代码执行漏洞：

  • CVE-2026-109618：OOM（内存耗尽）处理不当导致内存破坏，最终可 RCE
  • CVE-2026-109619：请求结束后全局状态未正确清理，形成 use-after-free，最终可 RCE

两个漏洞的 CVSS v4.0 评分均为 9.2（Critical），社区将它们合称为 PHP2Shell。需要说明的是，PHP2Shell 是媒体和安全厂商使用的昵称，PHP 官方公告中主要使用 CVE 编号。

这次漏洞的特殊之处在于：问题不在 WordPress、Laravel 或某个插件里，而在 PHP 解释器本身。因此受影响的不是某一个应用，而是几乎所有用 PHP 处理 Web 请求的站点。本文基于官方安全公告和公开研究整理，不包含利用代码，重点放在原理理解、影响判断和处置上。

一、事件速览

项目 内容
披露/修复时间 2026 年 10 月 21 日 14:00 UTC
漏洞编号 CVE-2026-109618、CVE-2026-109619
漏洞类型 内存破坏 / use-after-free，均可导致 RCE
严重等级 CVSS v4.0 9.2（Critical）
攻击前提 网络可达，无需认证，无需用户交互
受影响组件 PHP 核心，而非某个 CMS 或框架
修复版本 PHP 8.5.12、8.4.27、8.3.36、8.2.35
官方态度 升级是唯一完整的修复方式

官方公告：https://www.php.net/archive/2026.php#2026-10-21-5

二、为什么这次影响这么大

1. 漏洞位于 PHP 核心

只要应用最终由存在漏洞的 PHP 解释器执行，WordPress、Drupal、Joomla、Magento、Laravel 等应用都会继承这个风险。攻击者不需要先找到一个插件漏洞，也不要求目标应用本身存在上传、反序列化或 SQL 注入问题。

2. 部分场景可在应用代码执行前触发

官方确认，在 Apache mod_php 环境下，攻击者可以发送特制 HTTP 请求，在应用代码真正运行之前触发漏洞。这也是 mod_php 被认为风险最高的原因：应用层的鉴权、WAF 规则和框架中间件都可能来不及介入。

3. 共享主机和容器放大了排查难度

共享主机、控制面板、CI/CD 构建镜像、Docker 容器和各类一体化环境中，经常存在多个 PHP 版本并存的情况。运维人员很容易只升级了 CLI，却漏掉真正处理 Web 请求的 FPM 或 mod_php。

4. 旧版本覆盖范围大

受影响的版本包括修复版本之前的所有 8.2/8.3/8.4/8.5 分支。PHP 8.1 及更早版本已经停止官方支持，不会获得正式的安全版本；官方只提供了 7.4、8.0、8.1 的源码回移分支，需要发行版或厂商自行打包。

三、CVE-2026-109618：OOM 处理导致的内存破坏

根因

PHP 在遇到内存耗尽（OOM）时，会通过 longjmp() 提前跳出当前执行上下文。问题在于，请求处理过程中的某些阶段，内存可能已经“可达”，但还没有完成初始化。如果此时发生分配失败，提前退出路径没有正确记录这个状态，请求内存就会停留在非法状态。

后续的请求关闭/清理流程可能把这块未正确初始化的内存当作有效数据去读取或分支，最终造成内存破坏。攻击者可以通过精心构造的请求，把这种状态导向可控的代码执行路径。

触发思路

官方公告提到，特制的 multipart 请求可以在看似没有超过 PHP 配置限制的情况下触发 OOM，例如：

  • 请求没有可用的 Content-Length，却能通过初始的 post_max_size 检查；
  • 构造大量 part header，让实际内存消耗远高于请求在线路上的大小；
  • 利用空文件上传控件不计入 max_file_uploads、但仍会创建元数据数组的特性；
  • 使用嵌套字段名放大数组构造带来的内存开销。

应用层也可能因为攻击者输入触发大对象或重复分配，从而间接制造 OOM。不同 PHP 构建、扩展、前端行为和内存分配器布局都会影响利用的稳定性。

哪些 SAPI 受影响

  • **Apache mod_php**：已确认可通过 HTTP 实现未认证 RCE，且在默认 PHP 输入和内存限制下验证成功。
  • PHP-FPM：源码分析认为存在风险，但官方公告中尚未展示完整的 FPM 利用链；FPM 在请求启动失败时通常会退出子进程，降低了可利用性。
  • FrankenPHP：被认为可能受到与应用无关的攻击影响。
  • LSAPI：模型上类似 FPM，应用相关利用“可能但未验证”。

修复补丁移除了 OOM 路径中的 longjmp()，改为在下一个 VM 安全点触发延迟的软 OOM，并在更高阈值处使用 _exit() 立即退出，避免带着非法状态继续清理。

四、CVE-2026-109619：残留全局状态导致的 use-after-free

根因

PHP 的常驻 worker 会在多个请求之间复用进程。错误状态、session 状态、对象状态和扩展状态等全局数据，可能仍然指向上一个请求拥有的内存。正常情况下，这些状态必须在释放请求堆之前被清理掉。

但在某些致命错误、OOM 或诊断路径中，重置逻辑可能被跳过，或者重置后又被重新写入，导致请求私有状态残留在全局可访问的位置。等 PHP 释放请求内存后，后续请求在正常初始化之前访问到这些残留指针，就形成了 use-after-free。攻击者可以通过精心布置堆布局，把这个 UAF 提升为远程代码执行。

利用条件

这个漏洞需要“生产者”和“消费者”落在同一个 worker 上：

  1. 第一个请求触发致命错误、解析/编译失败、require 失败、执行超时或 OOM，留下脏状态；
  2. PHP 释放该请求的内存，但全局状态仍然引用它；
  3. 后续请求由同一个 worker 处理，并在正常初始化之前访问到残留状态；
  4. 攻击者通过堆布局控制被复用的内存内容。

已确认的消费路径包括早期 INI 诊断和 session upload progress。其中 session upload progress 默认开启，而且不要求应用主动调用 session_start()，因此暴露面值得特别注意。

哪些 SAPI 受影响

  • **Apache mod_php**：在 PHP 8.5 开启 fatal_error_backtraces 时，已确认可通过 fatal-error backtrace 路径实现 RCE。
  • PHP-FPM：通过 session 生命周期路径，在 mod_php 和 FPM 上均验证了 RCE；但需要合适的应用操作。
  • LSAPI：可能通过早期特殊 INI 环境值触发，属于条件性候选。
  • FrankenPHP：默认配置下未建立等价的早期配置消费路径，但官方明确表示这不代表免疫。

修复补丁扩大了请求结束时要重置的状态集合，确保不会把请求私有状态带入后续请求的预初始化阶段。

  3. 如果短期无法迁移，至少将服务从公网隔离，并制定明确的迁移期限。

八、无法立即升级时的临时缓解

官方明确强调：以下措施都不能替代升级，只能降低特定攻击路径的暴露面。

针对 CVE-2026-109618

但这不是完整缓解：如果底层 mmap() 等分配失败，漏洞路径仍可能被触发。设置后要确保 FPM pool、目录级配置和应用配置不会重新启用有限的内存限制，并重启所有 worker。

同时建议：

还需要在前端/反向代理层限制：

  • 解码后的请求体大小；
  • 输入字段数量；
  • multipart part 数量；
  • 每个 part 的 header 数量；
  • 嵌套深度；
  • 没有可用 Content-Length 的请求。

如果应用完全不需要上传，可以直接在边界层阻断 multipart 请求。

不要使用 RLIMIT_AS 或 RLIMIT_DATA 来“限制内存”，因为这些限制本身可能触发漏洞所需的分配失败路径。cgroup/容器内存限制可以作为可用性边界，但不能保证阻止漏洞触发。

九、被入侵后的排查方向

如果服务器在漏洞披露后、完成升级前一直暴露在公网，建议按“可能已被入侵”处理，而不只是升级了事。

重点检查：

  • Web 服务器进程是否启动了 sh、bash、curl、wget 等异常子进程；
  • Web 根目录是否出现未知 PHP 文件、webshell 特征或异常修改时间；
  • PHP-FPM/Apache 是否出现异常崩溃、worker 反复重启；
  • 访问日志中是否有大量异常 multipart 请求、超大 header、多 part 请求，或异常的 session.upload_progress 请求；
  • 是否有异常外连、下载行为或计划任务；
  • 应用配置中的数据库密码、API Key、云凭证是否可能被读取。

如果发现可疑迹象，应尽快隔离主机、保留日志和内存/磁盘证据，并轮换该服务器可访问的凭证。排查时间范围要覆盖补丁发布之前，而不是只看升级之后的日志。

十、常见误区

“我用的 WordPress 已经更新了插件和主题，应该没事。”

不成立。漏洞在 PHP 运行时，不在 WordPress 插件里。必须升级 PHP 本身。

“服务器上的 php -v 已经是新版本了。”

不一定。CLI、FPM、mod_php 可能是不同版本。必须确认处理 Web 请求的 SAPI。

“有 WAF / CDN 规则，可以先不升级。”

WAF 和虚拟补丁只能争取时间，无法覆盖所有攻击路径，官方也只把升级视为完整修复。

“关闭 session.upload_progress 就安全了。”

这只针对 CVE-2026-109619 的一个已知消费路径，不能修复 CVE-2026-109618，也不能覆盖其他状态残留路径。

“PHP 8.1 已经 EOL，所以不会被盯上。”

恰恰相反。EOL 版本没有官方修复，仍然是可利用目标，而且往往缺少持续的安全监控。

“CVSS 攻击复杂度是 High，所以可以先观望。”

复杂度高不等于不能被利用。公开 PoC 已经出现，攻击者可以反复尝试；对于暴露在公网的核心业务，等待的成本远高于升级。

十一、时间线

时间 事件

2026-10-20 PHP 发布提前通知；漏洞细节在 embargo 结束前泄露
2026-10-21 07:30 UTC 左右 安全厂商观察到攻击尝试和探测流量
2026-10-21 14:00 UTC PHP 发布 8.5.12、8.4.27、8.3.36、8.2.35
2026-10-21 公开 PoC 开始出现；PHP 官方表示尚未收到成功利用报告

截至 10 月 21 日，PHP 官方尚未确认在野成功利用，但公开 PoC 和探测流量已经出现。对于公网 PHP 服务，应该按“随时可能被利用”的优先级处理。

十二、处置清单

  • 盘点所有 PHP 实例和 Web SAPI，而不只是 CLI
  • 升级到 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 或厂商安全版本
  • 重启 Apache、FPM、容器和所有 PHP worker
  • 验证 Web 请求实际使用的 PHP 版本
  • 对 8.1 及更早版本制定迁移或厂商补丁方案
  • 无法立即升级的实例先隔离或下线
  • 检查异常进程、webshell、日志和外连
  • 如有失陷迹象，轮换数据库密码、API Key 和云凭证
  • 持续关注 PHP 官方后续公告和厂商通告
