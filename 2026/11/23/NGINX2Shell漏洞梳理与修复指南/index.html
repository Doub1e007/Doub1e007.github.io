nginx 也翻车了：9.2 分的 NGINX2Shell 漏洞到底有多严重？（CVE-2026-123007 / CVE-2026-123633）

发表于2026年11月23日|更新于2026年11月23日|安全
|浏览量:

2026 年 11 月 18 日，F5 / nginx.org 发布安全更新，修复了 9 个 nginx 漏洞，其中两个位于 HTTP/2 实现、可导致未授权远程代码执行的问题最受关注：

  • CVE-2026-123007：HTTP/2 连接级流控计数器下溢，造成堆越界读写，可 RCE
  • CVE-2026-123633：HTTP/2 连接关闭路径中的 use-after-free，可 RCE

社区把这一组漏洞称为 NGINX2Root，把其中的 RCE 部分称为 NGINX2Shell。需要说明的是，这两个名字都不是官方命名：nginx 官方公告使用 CVE 编号，nginx2shell 是媒体和安全厂商的昵称；nginx2root 则额外假定了攻击者能再链上一个 Linux 本地提权漏洞。本文基于官方公告和公开研究整理，不包含利用代码，重点放在原理理解、影响判断和处置上。

二、先搞懂 HTTP/2 的流控

HTTP/2 用滑动窗口做流量控制，避免发送方把接收方的缓冲区打爆。这里有两个层级的窗口：

  • 连接级窗口（connection flow-control window）：所有 stream 共享；
  • Stream 级窗口：每个 stream 各自独立。

发送方每发送一个 DATA 帧，就从对应窗口里扣掉相应字节数；接收方处理完数据后，通过 WINDOW_UPDATE 帧把额度还回来。窗口的初始值默认是 65535 字节，上限是 2^31 - 1（0x7FFFFFFF）。

问题就出在“还额度”这件事上：如果发送方对同一个 DATA 帧重复退款，窗口计数就会超过协议规定的上限，后续的边界检查又因为无符号运算回绕而失效。这正是 CVE-2026-123007 的核心。

三、CVE-2026-123007：流控计数器下溢

根因

当 nginx 向客户端发送响应时，如果 TCP 出现背压（客户端接收慢、send() 无法写满），已经排队的 DATA 帧会暂时留在发送队列里。此时连接级窗口的额度已经扣过了，但数据还没真正发出去。

攻击者的操作顺序大致是：

  1. 制造背压，让 DATA 帧滞留在队列中；
  2. 发送大量 WINDOW_UPDATE，把连接窗口重新抬高；
  3. 通过 RST_STREAM 取消流，或修改 SETTINGS_INITIAL_WINDOW_SIZE 让请求提前结束。

请求结束时会进入 ngx_http_v2_filter_cleanup() 清理逻辑。问题在于，清理函数会把仍在队列中、额度已经扣过一次的 DATA 帧再退款一次。一次请求里可能发生多次这样的“双重退款”，连接级 send_window 就被推过了 0x7FFFFFFF。

接下来是第二步：nginx 对 WINDOW_UPDATE 的合法性检查本来是 window <= 2^31 - 1 之类的边界判断，但当 send_window 已经超出上限时，右侧的表达式的值会变成负数，再按无符号数比较时发生回绕，检查反而通过了。攻击者可以借此把窗口值继续放大到 64 位地址空间的高半区。

从整数错误到内存破坏

窗口值最终在 TLS 输出路径中被强制转换成有符号的 off_t。一个本应巨大的无符号数变成了负数长度，memcpy / memmove 的边界计算随之出错，形成大范围的堆越界读和越界写。表现出来的现象通常是 worker 进程崩溃（DoS），而在满足条件时可以被进一步利用为代码执行。

按照公开分析，1.31.9 的修复方式是引入 send_queued 计数：退款时只能退“真实仍在队列中的额度”，并且只对 DATA 帧退款，从根上消除重复退款。

为什么这个洞藏了 11 年

HTTP/2 从 nginx 1.9.5（2015 年 9 月）开始支持，而这段流控记账逻辑长期没有大的改动。流控代码路径分支多、状态组合复杂，正常测试很难覆盖“背压 + 窗口更新 + 流取消”同时出现的时序，这类竞态型内存错误就容易长期潜伏。

四、CVE-2026-123633：连接复用标记导致的 UAF

第二个 RCE 的成因更“工程化”一些。

nginx 在处理 HTTP/2 连接时，会用 ngx_reusable_connection(c, 1) 把连接标记为“可复用”。当客户端只发送了部分 HEADERS 帧、请求尚未完成时，这个标记就已经被设置，而后续创建 stream 的路径没有清除它。

在反向代理场景下，当 worker 的可用连接数紧张时，drain_connections 会尝试回收连接。它看到一个“可复用”的连接，就把它关掉并释放内存——但这条连接其实还在处理请求。后续代码继续访问已释放的连接对象，形成 use-after-free。

这个漏洞主要影响反向代理配置，并且需要连接槽位紧张这一条件。修复只有一行：在创建 stream 时清除 reusable 标记。

六、影响范围

nginx 开源版

分支 受影响版本 修复版本
stable 1.9.5 – 1.30.6 1.30.7
mainline 1.31.0 – 1.31.8 1.31.9

CVE-2026-123007 从 2015 年的 1.9.5 起就存在；CVE-2026-123633 则从 1.19.7 之后引入。也就是说，几乎所有支持 HTTP/2 的 nginx 版本都在范围内。

NGINX Plus

F5 公告中，37.0.x 需升级到 37.0.8.1，37.1.x / 37.2.x 需升级到 37.3.0.1 及以上；已 EOL 的 R33–R36 分支没有官方修复。具体以 F5 的 K000163926（-123007）和 K000163928（-123633）公告为准。

容易被忽略的“内嵌 nginx”

版本号不能只看 nginx -v。下面这些位置都可能带着有问题的 HTTP/2 代码：

  • Kubernetes Ingress Controller、Gateway Fabric 等 F5 自家产品；
  • OpenResty、APISIX、Kong 等基于 nginx/OpenResty 的网关；
  • 各类 WAF、负载均衡、CDN 回源组件中内嵌的 nginx；
  • 容器镜像、CI 构建产物、离线安装包。

这些产品的版本号与上游 nginx 不是一一对应的，必须看厂商自己的安全公告，不能只拿 1.30.7 去比对。

七、自查：我的 nginx 真的受影响吗

漏洞利用有三个硬前提：版本在范围内、HTTP/2 模块被编译进来、监听端口实际启用了 HTTP/2。三者缺一不可。

1. 查版本和模块

nginx -V 的输出里如果没有 --with-http_v2_module，说明这个构建根本不支持 HTTP/2，CVE-2026-123007 不适用于它（但版本本身仍应升级，因为同批还有别的洞）。

2. 查配置里是否启用了 HTTP/2

可能的写法有两种：

只要任意一个 server 块启用了 HTTP/2，并且该端口对公网可达，就应该按受影响处理。

3. 从外部确认是否协商了 h2

输出 ALPN protocol: h2 表示确实协商到了 HTTP/2。注意要测源站地址，而不是 CDN 的边缘节点。

4. 查包管理器、容器和所有实例

别只看一台机器：负载均衡后面的多台源站、灰度环境、备份机、临时测试环境，都可能还跑着旧版本。

八、修复步骤

第一步：升级

优先使用发行版或官方软件源，等待厂商回移补丁；如果用的是官方源码包，直接升级到 1.30.7 / 1.31.9。

源码编译时务必校验 PGP 签名，不要从第三方镜像随便下载：

Docker 场景应更新基础镜像并重新构建，而不是进容器里手动替换二进制。

第二步：完整重启，而不是 reload

这一步很容易做错。nginx -s reload 只是让 master 重新读取配置并 fork 新 worker，master 进程内存里仍然是旧的可执行文件，新 worker 也就还是旧代码。必须重启整个进程：

容器环境用滚动重启，并确认旧容器/Pod 已经全部退出。

第三步：验证

确认版本号已经是安全版本，并且 worker 的启动时间在升级之后。再看一眼监听配置，确认业务没有被误伤。

第四步：处理无法升级的旧分支

已经 EOL、厂商不再提供补丁的版本，只有两条路：迁移到受支持版本，或者退而求其次关闭 HTTP/2 并隔离暴露面。不要指望“版本老就没人打”——老版本恰恰缺少持续监控。

九、无法立即升级时的临时缓解

官方给出的有效缓解是关闭 HTTP/2。它不能替代升级，但能同时阻断 CVE-2026-123007 和 CVE-2026-123633 的已知攻击路径。

  • 如果源站只能通过 CDN 访问，可以在边界层限制直连，但这依赖网络配置正确，不能当成默认安全。

十、如果怀疑已经被打

CVE-2026-123007 是内存破坏，不是“往 web 目录写文件”的漏洞。所以排查思路和 webshell 事件不完全一样：

  • 关注 nginx worker 是否出现异常 SIGSEGV、core dump、反复重启；
  • 检查是否有异常长连接、超大流量、密集 WINDOW_UPDATE 的 HTTP/2 会话（普通 access log 看不到帧级别细节，需要抓包、eBPF 或厂商检测规则）；
  • 检查 nginx 及其子进程有没有拉起 sh、bash、curl、wget 等异常子进程；
  • 检查 /tmp、/dev/shm 下是否有可疑文件，计划任务、LD_PRELOAD、动态链接器配置是否被改；
  • 检查异常外连和数据外传；
  • 如果确认有可疑迹象，先保留内存、core 和日志证据，再重启服务，并轮换该机器可访问的凭证。

另外要警惕：漏洞披露后出现了不少打着“nginx2root exploit”旗号的仓库，其中一些是恶意代码或钓鱼。不要在生产环境或自己的开发机上运行来源不明的利用程序。

十一、常见误区

“我只是静态文件服务器，没有后端，不会有 RCE。”

不成立。CVE-2026-123007 影响的是 HTTP/2 编解码和 TLS 输出路径，Wiz 就是在只提供静态文件的官方构建上演示了利用，不需要 PHP、Java 或任何应用。

“前面有 CDN / WAF，源站就安全。”

不一定。CDN 终止 HTTP/2 后，攻击流量在边缘就被拆成了 HTTP/1.1，确实会让利用条件难以成立；但这依赖 CDN 的具体实现，而且源站如果可以被直连绕过，防护就失效了。CDN 只能争取时间，不能替代升级。

“nginx -s reload 过了，补丁就生效了。”

不生效。reload 不会替换 master 进程里的旧代码，必须完整重启。

“版本不在受影响范围就万事大吉。”

版本只是第一个条件。还要确认 HTTP/2 模块是否编译、端口是否启用 h2、是否可被直接访问。反过来，版本在范围内也不代表一定能打，需要背压、窗口更新、流取消等时序条件同时满足。

“CVSS 攻击复杂度是 High，可以先观望。”

公开 PoC 已经出现，Wiz 也展示了带 ASLR 绕过的完整利用链。对暴露在公网的核心入口，等待的成本通常高于升级。

“看到 web 目录里有 nginx2shell.php 就是中招了。”

这个漏洞不写 webroot。可疑文件更可能是别的入侵途径留下的；同样，没有可疑文件也不代表没被打。判断依据应该是 crash、内存取证、帧级流量和进程行为。
